# Zero-downtime migration of `users` (MySQL 5.7 to PostgreSQL 16)

Here's how I'd approach it. The core idea: keep MySQL as the source of truth while a continuous replication stream fills and then follows a Postgres copy. Prove the two match. Then move reads, then writes, with a reverse stream ready so you can roll back at any point. "Zero downtime" in practice means no maintenance window. You should still plan for a write pause of a few seconds at cutover, or for dual-writes if even that is unacceptable. I explain the difference below.

## Questions I would ask

1. **Is only `users` moving, or is this the first table of a full MySQL to Postgres move?** Default: only `users` moves now, and other tables stay in MySQL for a while. That has big consequences. Any SQL JOIN between `users` and other MySQL tables stops working, and so do foreign keys that point at `users.id`.
2. **What does "zero downtime" mean to you?** Is a write pause of roughly 2 to 10 seconds acceptable (requests queue or retry, nothing errors)? Or must every write succeed with no added latency? Default: a sub-10-second write pause is acceptable, and reads stay up throughout.
3. **How do applications reach the database?** A single service or several? An ORM? Raw SQL? Default: one or two services through an ORM, with some raw SQL that needs auditing.
4. **Hosting.** Self-managed or RDS/Aurora/Cloud SQL? Default: managed (for example RDS MySQL 5.7 to RDS Postgres 16). If so, AWS DMS is available as an alternative to Debezium.
5. **Is binlog already `ROW` format with `binlog_row_image=FULL`, and how long are binlogs retained?** Default: unknown. Phase 0 checks it.
6. **Write rate and row size.** Default: a few hundred to a few thousand writes per second, rows under 2 KB. At 8M rows the initial copy is small (a few GB). The hard part is the change stream and the cutover, not the volume.
7. **Are there triggers, stored procedures or events on `users`, or other systems that read MySQL directly** (BI, ETL, other teams' services)? Default: assume some exist until the inventory is done.

## Phase 0: Inventory and prerequisites (about 1 week)

- Dump the exact DDL: `SHOW CREATE TABLE users`, indexes, triggers, FKs into and out of `users`.
- Grep every codebase for `users`, including raw SQL, reporting jobs and cron scripts. List every reader and writer.
- MySQL settings: `binlog_format=ROW`, `binlog_row_image=FULL`, `gtid_mode=ON` (helpful for resuming CDC), and binlog retention of at least 3 to 7 days so CDC can catch up after an incident.
- Check the data for things that break in Postgres:
  - `0000-00-00` dates and invalid datetimes. Postgres rejects them, so decide whether they map to NULL or a sentinel value.
  - Charset: `utf8` (3-byte) versus `utf8mb4`. Look for invalid byte sequences, which Postgres rejects.
  - Case-insensitive collations. MySQL's `email = 'Foo@x'` matches `foo@x`, Postgres does not. A `UNIQUE(email)` that held in MySQL may hold only because of the collation. Use `citext` or a unique index on `lower(email)`, and check for case-only duplicates *before* migrating.
  - Trailing-space semantics in `VARCHAR` comparisons (PAD SPACE in MySQL).
  - `TINYINT(1)` used as boolean, `ENUM`/`SET` columns, `UNSIGNED` ints (an unsigned INT needs `bigint` in Postgres), `DATETIME` with no timezone versus `timestamptz`.
  - `AUTO_INCREMENT` becomes `GENERATED BY DEFAULT AS IDENTITY`. Set the sequence well above MySQL's current max at cutover.
- Application-level SQL dialect issues: backtick quoting, `INSERT ... ON DUPLICATE KEY UPDATE` (becomes `ON CONFLICT`), `LIMIT x,y`, `IFNULL`, implicit type coercion, `GROUP BY` leniency, `LAST_INSERT_ID()` (becomes `RETURNING id`).

**Exit criterion:** a written column-by-column type map and a list of every code path that touches `users`.

## Phase 1: Target schema and tooling (about 1 week)

- Create the Postgres 16 table with the agreed type map. Create **only the primary key** at first. Build the secondary indexes after the bulk load, because that is much faster, then add constraints.
- Pick the replication tool:
  - **Debezium (MySQL connector) to Kafka to a JDBC sink or a small custom consumer.** My default. Mature, it handles snapshot plus binlog with a consistent offset, and you control the transforms.
  - **AWS DMS.** Less to operate if you are already on AWS. Weaker on type edge cases, so validate carefully.
  - **pgloader.** Only for the initial copy. It has no CDC.
- Make the sink apply changes **idempotently**: upsert by primary key, deletes by primary key, and drop any event whose source position is older than the last one applied for that row.

## Phase 2: Initial load and continuous replication (days)

1. Start CDC with an initial snapshot (Debezium `snapshot.mode=initial`, or a non-locking snapshot on InnoDB using a consistent read). This records the binlog position, so changes made during the copy are applied afterwards.
2. Let it catch up, then build the secondary indexes (`CREATE INDEX CONCURRENTLY` once the table is live), run `ANALYZE`, and add the unique constraints.
3. Monitor replication lag (seconds behind the binlog). Alert at more than 5 seconds.

## Phase 3: Verification (at least 1 to 2 weeks of steady replication)

- **Row counts**, continuously, allowing for lag.
- **Checksums per primary-key range.** Hash a canonical serialization of each row in chunks of 10k IDs on both sides and compare. Re-check any mismatched chunk after lag has drained. Tools: a custom script, or `pt-table-checksum`-style chunking logic. There is no off-the-shelf cross-engine tool I would trust blindly.
- **Shadow reads.** For a sample of production reads (say 1%), also query Postgres asynchronously, compare the results and log the differences. This catches application-level dialect bugs (collation, sort order of NULLs, timezone handling), not just data bugs.
- Put the application's Postgres data-access path through the full test suite against Postgres.

**Exit criterion:** zero unexplained mismatches for 7 consecutive days. Every explained mismatch has a documented fix.

## Phase 4: Move reads (gradual)

- Behind a feature flag, send reads that tolerate staleness to Postgres: 1%, then 10%, then 50%, then 100%. Read-your-own-writes paths (for example "update profile, then show profile") stay on MySQL until writes move, or they must tolerate the replication lag.
- Watch p99 latency and error rates, and watch Postgres connection counts. Put PgBouncer in front of Postgres from day one. Postgres handles a high connection count much worse than MySQL does.

## Phase 5: Move writes (the actual cutover)

**Option A: short write freeze (default, simplest and safest).**
1. Pre-stage everything: set up a reverse CDC stream (Postgres logical replication, or Debezium on Postgres, to MySQL), configured but paused. The flag that routes writes to Postgres is ready.
2. Low-traffic window. Flip the app to *reject or queue* writes to `users` for a moment (a "read-only users" flag, with client retries).
3. Wait until forward CDC lag is 0 and checksum the most recently changed rows.
4. Set the Postgres identity sequence to `max(id) + safety gap`.
5. Flip writes to Postgres. Start the reverse stream so MySQL keeps receiving changes and stays a rollback target. Stop forward CDC.
6. Lift the freeze. The expected write pause is a few seconds.

**Option B: dual-write (only if the answer to question 2 is "no pause at all").** The app writes to both databases with one of them as primary, reconciles asynchronously, and a reconciliation job repairs drift. This is far more code and failure modes: partial failures, ordering, ID generation (you need IDs that don't depend on either database's sequence). I would avoid it unless it is really required.

## Phase 6: Rollback window and decommission (2 to 4 weeks)

- Rollback = flip the write flag back to MySQL. The reverse stream has kept MySQL current. Rehearse this in staging, and once in production during Phase 4 for reads.
- Keep running the checksums in reverse (Postgres to MySQL).
- After 2 to 4 quiet weeks: stop the reverse stream, revoke write grants on the MySQL `users` table, keep a final dump, and drop the table later.

## Cross-cutting concerns

- **FKs and JOINs across engines.** If other MySQL tables reference `users.id`, they lose referential integrity once writes move. Options: enforce it in the application, keep a read-only replica of `users` in MySQL fed by the reverse stream (which also keeps the JOINs working), or migrate the related tables together. With the default from question 1, I would keep the reverse-replicated copy in MySQL until the other tables move.
- **Rehearsal.** Run the whole sequence end to end against a production-sized copy in staging at least once, including rollback, and time each step.
- **Observability.** One dashboard showing CDC lag, mismatch count, shadow-read diff rate, error rate per database, and Postgres connection and lock metrics.
- **Security and PII.** `users` almost certainly holds PII. Encrypt the Kafka topics or DMS channel in transit and at rest, set retention, and remove any topic copies afterwards.

## Main risks

1. Collation and uniqueness differences on `email`/`username`. Find them in Phase 0, not at cutover.
2. Hidden consumers of MySQL `users` (BI, other teams) that break silently.
3. Replication lag spikes under heavy writes during the snapshot. Size the sink for at least 3 times peak write rate.
4. Sequence/ID collisions at cutover.
5. Postgres connection exhaustion. Use PgBouncer.
